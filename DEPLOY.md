# Deploying SalesMotion

Backend on **Render**, frontend on **Cloudflare Pages**, database on **MongoDB Atlas**.

The two halves are deployed separately and have to be pointed at each other. Do
the backend first — you need its URL before the frontend can be built.

---

## 1. MongoDB Atlas

Render does not give a web service a fixed outbound IP unless you pay for it, so
the app cannot connect until Atlas is told to accept it.

1. Atlas → **Network Access** → **Add IP Address**.
2. Either add Render's outbound IPs for your region (listed in the Render
   dashboard under **Connect → Outbound**), or `0.0.0.0/0` to allow any host.
   `0.0.0.0/0` is only as safe as your database password — use a long one.
3. Copy the connection string from **Database → Connect → Drivers**. It must end
   with the database name, e.g. `.../salesmotion?retryWrites=true&w=majority`.

If this step is wrong the backend exits on boot with
`❌ MongoDB connection error` — that is deliberate, so a broken instance never
goes live serving errors.

---

## 2. Backend on Render

The repo has a `render.yaml` blueprint, so you do not have to fill in the service
settings by hand.

**Render dashboard → New → Blueprint → select this repo.**

It creates a web service with `rootDir: backend`, `npm ci --omit=dev`,
`npm start`, and a health check on `/api/health`.

Then set the secrets it deliberately left blank (**Environment** tab):

| Variable | Value |
|---|---|
| `MONGODB_URI` | the Atlas string from step 1 |
| `FRONTEND_URL` | leave blank for now — filled in at step 4 |
| `GROQ_API_KEY` | from console.groq.com |
| `GEMINI_API_KEY` | from aistudio.google.com/apikey |
| `NEWS_API_KEY` | from newsapi.org |
| `FINNHUB_API_KEY` | from finnhub.io |
| `SUPABASE_URL` / `SUPABASE_SERVICE_KEY` | optional — the app boots fine without them |

`JWT_SECRET` is generated by Render automatically. **Do not regenerate it later**
— that signs every existing user out.

`FRONTEND_URL` is required in production. The service will refuse to start
without it and tell you so in the deploy log, so expect the first deploy to fail
until step 4. That is fine.

Note the service URL, e.g. `https://salesmotion-api.onrender.com`.

### Why `starter` and not `free`

Reports finish generating **after** the HTTP response is sent. The free plan
spins the instance down after ~15 minutes idle, which kills any generation still
running and adds a ~50 second cold start to the next request. On `starter` the
instance stays up. Either way no report gets stuck forever — the sweeper
(below) resolves orphans — but on free they fail instead of finishing.

## 3. Frontend on Cloudflare Pages

**Cloudflare dashboard → Workers & Pages → Create → Pages → Connect to Git.**

| Setting | Value |
|---|---|
| Framework preset | Create React App |
| Build command | `npm run build` |
| Build output directory | `build` |
| Root directory | `frontend` |

Then **Settings → Environment variables**, and add to **both** Production *and*
Preview:

```
REACT_APP_API_URL = https://salesmotion-api.onrender.com/api
```

Two things that catch people out:

- The trailing **`/api` is required**; a trailing slash after it is not.
- CRA bakes `REACT_APP_*` values in at **build** time. Changing this variable
  does nothing until you trigger a fresh deploy.

`frontend/.node-version` pins Node 22 for the build, and
`frontend/public/_redirects` sends every path to `index.html` so that refreshing
on `/reports/<id>` works instead of 404ing.

Note the site URL, e.g. `https://salesmotion.pages.dev`.

---

## 4. Point them at each other

Back in Render, set `FRONTEND_URL` to the Cloudflare URL and redeploy:

```
FRONTEND_URL=https://salesmotion.pages.dev,https://*.salesmotion.pages.dev
```

The second entry is a wildcard covering Cloudflare's preview deployments, which
each get their own subdomain. Without it, previews work but every API call in
them is blocked by CORS. Drop it if you do not want previews reaching production
data — which is a reasonable choice.

---

## 5. Check it

```bash
curl https://salesmotion-api.onrender.com/api/health
```

Expect `200` and `"mongodb": "connected"`. A `503` means the database is
unreachable — recheck step 1.

Then open the frontend, sign in, and **refresh the page on a report** — that is
the specific thing `_redirects` fixes.

---

## What runs automatically

- **Stuck report recovery.** A report interrupted by a restart or redeploy is
  marked `failed` with "Generation was interrupted…" instead of spinning
  forever. Checked every 5 minutes; anything pending for over 15 minutes is
  swept. Tune with `REPORT_STALE_AFTER_MS` / `REPORT_SWEEP_INTERVAL_MS`.
- **Graceful shutdown.** On redeploy, in-flight requests finish and MongoDB
  closes cleanly before the process exits.
- **Rate limits.** 600 requests / 15 min per IP overall, 30 sign-in attempts /
  15 min, 40 report generations / hour. All well above normal use; raise via
  `RATE_LIMIT_GLOBAL`, `RATE_LIMIT_AUTH`, `RATE_LIMIT_REPORTS` with no code
  change. The report limit is the one that caps AI spend.

## Known limitation: generated PDFs

PDFs are written to the instance's local disk, which Render wipes on every
deploy. This is handled rather than broken: when a stored PDF is missing, the
download route re-renders it from the saved analysis with **no AI calls
repeated** — the download is just slower that once.

It becomes a real problem only if you scale past one instance, since instance A's
files are not on instance B. At that point move `reportGenerator`'s output to
object storage (S3 or Supabase Storage).
